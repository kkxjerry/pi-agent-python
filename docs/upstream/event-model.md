# Event model — pi v0.84.4

The upstream system exposes two related streams: provider-level assistant events
and Agent-level lifecycle events. Their separation is a hard architectural
boundary.

## Provider assistant events

The provider-neutral stream uses these event families:

```text
start
text_start / text_delta / text_end
thinking_start / thinking_delta / thinking_end
toolcall_start / toolcall_delta / toolcall_end
done | error
```

`start.partial.stopReason` is `pending`. Delta events carry the latest partial
assistant message. A terminal `done` or `error` carries the final message and
also resolves the stream result.

### Tool Call deltas

Tool arguments arrive as incomplete JSON fragments. Delta events may expose a
best-effort partial object for rendering, but the Agent must not validate or
execute the call until the final Tool Call block is available.

### Terminal contract

- A terminal event is still yielded to stream consumers.
- `result()` resolves independently to the terminal assistant message.
- pushes after completion do not alter the result;
- producer exceptions are converted to terminal error messages rather than
  leaving consumers blocked forever.

## Agent events

Agent Core wraps provider events with:

```text
agent_start
turn_start
message_start
message_update
message_end
tool_execution_start
tool_execution_update
tool_execution_end
turn_end
agent_end
```

`message_update` retains the underlying assistant event type. Tool progress is a
separate event and is not automatically appended as a transcript message.

## Text-only event order

```text
agent_start
turn_start
message_start(user)
message_end(user)
message_start(assistant pending)
message_update(start/deltas/end)
message_end(assistant final)
turn_end
agent_end
```

Continuation differs: existing user/ToolResult messages are context, not newly
emitted messages, so their start/end events are omitted.

## Tool event order

For the sequential path:

```text
message_end(assistant with Tool Call)
tool_execution_start
[tool_execution_update...]
tool_execution_end
message_start(ToolResult)
message_end(ToolResult)
turn_end
turn_start
...
```

For parallel execution, completion events may be out of order while transcript
ToolResult messages remain in original call order. The Phase 2 fixture
`parallel_out_of_order.jsonl` locks this distinction for Phase 8.

## Error representation

Unknown tools, invalid arguments, tool exceptions, and truncated Tool Calls are
represented as `isError=true` ToolResult messages so the model can recover. A
provider failure is represented as a final assistant message with
`stopReason=error` or `aborted`.

## Subscriber behavior

The future stateful Agent will deliver events to subscribers in registration
order and await async subscribers. This creates a deterministic state-update
barrier; UI observers cannot race ahead of transcript state.
